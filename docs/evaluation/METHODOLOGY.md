# Evaluation methodology

`npm run db:benchmark` runs against the configured PostgreSQL database and records PostgreSQL/PostGIS versions, memory/edge counts, host metadata, and benchmark parameters. It performs five sequential repetitions by default (`BENCHMARK_RUNS=1..20`) and captures eight actual `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` plans per repetition:

- A 150 m PostGIS geography corridor predicate with a normal planner-selected plan.
- The same predicate with index and bitmap scans disabled for a controlled sequential-plan comparison. Production indexes remain present; this is not an index-drop experiment.
- Associative recall at depths 1, 2, and 3 with a 0.01 activation threshold.
- Fading materialized-view retrieval and its equivalent direct query.
- Timeline retrieval over the 30-day interval ending at the dataset's latest event time.

The runner separately times initial fading materialized-view creation by obtaining the live view definition and creating a probe in a process-unique schema inside a transaction. It drops only that generated schema before commit. It also measures a live `REFRESH MATERIALIZED VIEW fading_memories_mv`. No production tables or data are removed by these measurements.

The 1,200-memory run uses the preserved local Compose database. The 10,000-memory run was generated in a separate temporary PostgreSQL/PostGIS/pg_cron container with its own database and no reused volume; the container was removed after its JSON and Markdown outputs were saved. To repeat at 10K, create a fresh isolated database, run migrations, run `npm run db:seed -- --large`, then run `BENCHMARK_LABEL=10000 npm run db:benchmark` with that database's `DATABASE_URL`. The seed command refuses to add data to a nonempty database.

The runner writes the latest report to `RESULTS.md` and `latest.json`; set `BENCHMARK_LABEL=1200` or `10000` to also preserve labeled artifacts. JSON includes every per-run plan and timing plus mean, median, sample standard deviation, minimum, and maximum. Markdown reports medians and sample deviation. The 1,200- and 10,000-memory reports are `RESULTS-1200.md` / `latest-1200.json` and `RESULTS-10000.md` / `latest-10000.json`. Runs are sequential in one session and share evolving cache state; they are not independent cold-start samples. In the captured five-run reports, the candidate plan was a Bitmap Heap Scan and its median execution time was slightly below the controlled sequential scan at both sizes; sample spread and shared cache state mean this does not establish a general index benefit. Cache state, selectivity, planner estimates, hardware, and system load affect both plans.

For measurements with a fresh PostgreSQL shared buffer pool per sample, run `npm run db:benchmark:fresh-buffers` after building the Compose database image. The script creates a separate temporary PostgreSQL container and volume from that image, migrates and seeds a deterministic 1,200-memory dataset, records one benchmark repetition, restarts that isolated server between trials, and removes only its temporary container and volume. Set `FRESH_BUFFER_TRIALS=2..10` (default 5); add `-- --large` to seed 10,000 memories. Results are written under `docs/evaluation/fresh-buffer-trials/`. The runner reports nominal two-sided 95% Student t intervals for mean query execution, view creation, and refresh times. This interval assumes independent, approximately normal observations. Trials clear PostgreSQL `shared_buffers`; they do not clear the operating-system file cache, and they use one host with sequential trials. They must not be described as cold-disk trials or multi-hardware replication. The main `RESULTS.md` and primary Compose database are not used as output/data targets by this runner.

Five-restart 10,000-memory reports from this host are preserved at [`fresh-buffer-trials/10000/`](fresh-buffer-trials/10000/) (restart only) and [`fresh-buffer-trials/10000-page-cache-attempt/`](fresh-buffer-trials/10000-page-cache-attempt/) (advisory relation-file eviction requests). The latter reports files and bytes targeted per trial; successful requests do not prove pages left the OS cache. Both use the same host and deterministic dataset and are not independent hardware replications.

An opt-in Linux cache-eviction attempt is available with `FRESH_BUFFER_EVICT_PAGE_CACHE=1 npm run db:benchmark:fresh-buffers`. After each disposable database checkpoint, the runner mounts its data volume read-only into the small `PAGE_CACHE_EVICTOR_IMAGE` helper (default `python:3.12-alpine`) and calls `POSIX_FADV_DONTNEED` for regular files under PostgreSQL `base/` and `global/`. The machine must be able to pull the helper image the first time. Each JSON trial records success, file count, and byte count for the requests. This is a best-effort advisory: it does not confirm that the kernel removed every page, does not clear all host caches, and does not guarantee cold storage. Reports therefore label it a relation-file page-cache eviction *attempt*, never a cold-disk result. Omit the flag for the restart-only comparison.

To prepare cross-machine comparison, run the same seed size, query parameters, and cache mode on each machine, setting a distinct `MACHINE_LABEL`. For example, on each host run `MACHINE_LABEL=<host-label> FRESH_BUFFER_TRIALS=5 npm run db:benchmark:fresh-buffers -- --large`, then copy `docs/evaluation/fresh-buffer-trials/fresh-buffer-pools.json` to a unique path before the next run overwrites it. Compare the collected artifacts with `npm run db:benchmark:compare -- path/to/machine-a.json path/to/machine-b.json`; the command writes `CROSS_MACHINE_RESULTS.md` and `.json` (override with `BENCHMARK_COMPARISON_MARKDOWN` and `BENCHMARK_COMPARISON_JSON`). It rejects differences in memory count, cache strategy, route radius, pruning threshold, or query-plan set. Input order determines the percentage-change baseline. It records host platform, architecture, CPU count, memory, Node, and PostgreSQL metadata; results remain descriptive, host-specific observations.

This repository also has a manual [GitHub Actions workflow](../../.github/workflows/benchmark-fresh-buffers.yml) on `ubuntu-24.04` that runs the same five-trial 10,000-memory restart-only benchmark and uploads the raw artifact. Trigger it with `gh workflow run benchmark-fresh-buffers.yml --ref main -f trials=5`, download the resulting `fresh-buffer-10000-<run-id>` artifact, and compare it with the local [`10000/fresh-buffer-pools.json`](fresh-buffer-trials/10000/fresh-buffer-pools.json) using `npm run db:benchmark:compare -- local.json runner.json`. This provides a separate CI virtual machine, not guaranteed dedicated physical hardware; compare the recorded runner metadata and describe it as a cross-environment comparison.

Human evaluation has not been conducted. The [human-study protocol](HUMAN_STUDY_PROTOCOL.md) and [study runbook](study/STUDY_RUNBOOK.md) provide three frozen fictional scenario tasks, a balanced Latin-square schedule, an operator answer key, a read-only database compatibility check, and an answer-key-based CSV scorer. `npm run study:validate` checks the pack and prints its hashes; `DATABASE_URL=... npm run study:verify-db` confirms the current synthetic database supports the exact tasks; `npm run study:score -- responses.csv` computes aggregate results without saving raw rows; and `npm run study:power` explores exact conditional McNemar sample-size sensitivity for paired binary accuracy. Power output depends on assumed discordance rates and is not an approved sample-size justification. Institutional ethics review, consent, preregistration, pilot-supported inputs and a justified sample-size plan, recruitment, and actual participant data remain outstanding. No participant results are present in this repository.

Correctness is tested separately by `tests/database/algorithms.sql`, which executes database routines in a rollback transaction, and `tests/database/concurrency.sh`, which runs simultaneous PostgreSQL sessions to check reinforcement serialization and history logging. Playwright covers CRUD and the map, timeline, graph, review, settings, and database-backed API workflows in Chromium. The measurements do not establish a correctness rate or biological/cognitive validity.

## Synthetic algorithm ablations, calibration, and robustness

`DATABASE_URL=... npm run test:research-db` executes `tests/database/research-recall.sql` inside a transaction and rolls back its route and graph fixtures. It verifies route-distance plus half-open event-time intersection, route ordering, exact path activation math, alternate path ranking, cycle prevention, depth bounds, and result limits.

`DATABASE_URL=... npm run research:evaluate -- --seed=497` evaluates the production `spatiotemporal_memory_walk` and `associative_recall` SQL functions against a deterministic, labeled eight-memory graph. It changes strengths, edge weights, valence, route locations, and edges only inside a transaction. It explicitly rolls back before checking that memory, edge, and context counts match their pre-run values; only then does it write `docs/evaluation/research/RESULTS.json` and `RESULTS.md`. A failure also rolls back before exiting. `--out=/path` directs output elsewhere; `--seed=<uint32>` controls the deterministic location-noise and edge-removal sequences; `RESEARCH_REPETITIONS=1..20` controls repeated query observations.

The ablation section compares the baseline with disabled edge weights, neutralized target strength, neutralized valence, one-hop depth, and pruning thresholds. Temporal sensitivity invokes the production `apply_memory_decay` function at one, seven, and thirty elapsed days with a fixed coefficient of 0.2; outputs include top activation as well as retrieval metrics so fading remains visible when ranked-set quality is unchanged. Calibration sweeps five salience coefficients and four thresholds, ranks results by synthetic F1, reciprocal rank, then lower threshold and salience, and reports latency without using it to select a configuration. Radius sensitivity tests 25–1,500 m. Robustness scenarios add deterministic location noise, mark locations missing, and remove 25%, 50%, or 75% of edges in five seeded trials per level. Reported precision, recall, F1, and mean reciprocal rank use the explicit fixture labels; elapsed milliseconds are client-observed PostgreSQL round-trip measurements. They are generated test results, not human observations, biological calibration, cold-cache timings, or cross-hardware evidence.

The report also aggregates F1 and mean reciprocal rank across the five seeded edge-removal trials at each removal fraction, showing the arithmetic mean, sample standard deviation, and observed range. These are descriptive summaries of the five deterministic perturbations only. They are not confidence intervals and do not estimate population or participant variability.
